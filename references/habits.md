# 本地 Git 整理与 GitHub 上传 · 习惯与注意事项

每踩一次坑就往这里追加一条，写清「什么情况、怎么错、正确做法」。下面是初稿，用着用着按实际情况改。

## 红线

- 新建仓库必须带 README 和 `assets/readme/hero.svg`;用 `beautify-github-readme` 生成,不要等用户提醒。

- 每次升版本必须同步 GitHub Release:tag 与 `vX.Y.Z` 一致,notes 写清这版改了什么;没有 Release 不算发完。

- 每趟先取舍：用不到的技能不读、不写进本次记录，也不为了「走全流程」硬凑步骤；动手前用一句话说明这次用了哪些、哪些不用、为什么。
- 远端操作优先走 REST API:本机没装 `gh`,但 Windows 凭据管理器里有 GitHub token,`git credential fill` 取出来就能调。要调视觉效果、要人确认、或 API 限流时,再开浏览器带用户一起点。
- 凭据不进版本库：token、密码、`.env`、私钥、服务器地址列表。发现疑似文件先排除再提交，不抱侥幸。
- 凭据值也不写进这份工作流、不写进对话和日志；需要时只写「见哪个文件」。
- 同一个远端只留一个正本仓库，第二个副本要么归档、要么明确标成只读备份。
- 破坏性动作先问：强推、覆盖远端历史、删远端分支或标签、改仓库可见性、加协作者。
- 推完必须真验：重新看一次远端的分支和最新提交，`git push` 没报错不等于远端就是想要的样子。

## 踩过的坑

- `D:\AI\NewApi管理_repo` 看着像重复仓库，其实是主仓库的 worktree，推档案仓就靠它。判断重复前先看 `.git` 是文件还是目录、再跑 `git worktree list`，别按目录名猜。
- 本地 `main` 比远端多提交不一定是漏推。这套仓库的档案仓只收脱敏精选的改动，两端本来就不会一样。
- 技能目录还没 `git init` 时,`repo_scan.py audit` 会按「跑不动（退出码 2：不是 git 仓库根目录）」拒跑,不是脚本坏了;先初始化再体检。
- 建库时勾了 `auto_init`(初始化 README / .gitignore / license),首次 `push` 会被拒;用 API 建库默认不初始化,别再手点。
- 加了 README 或 LICENSE 会改变依赖哈希,引用它的工作流 `check` 会报「原技能已改动」。确认只是文件增减后重新 `link` 一次刷新基线,别让告警常驻。
- 公开仓库的 README 和 `SKILL.md` 别写同一个意思:结构校验器会把两份文字一起比,判成重复警告。README 换措辞换结构,规则细节留在 `SKILL.md`。
